# raft-sim: Raft consensus in Java, with a deterministic fault-injection simulator

A research-style study of one question: **how do you convince yourself a consensus implementation is
correct, and what slips past the tests you'd normally write?**

I implemented Raft (leader election and log replication) from the paper, then built a simulator that runs a whole
cluster in *logical time* with injected message loss, duplication, reordering, partitions and crashes, and an
invariant checker that watches every run for violations of Raft's safety properties.

> Inspired by *In Search of an Understandable Consensus Algorithm* (Ongaro & Ousterhout, USENIX ATC 2014),
> by deterministic simulation as used in FoundationDB (SIGMOD 2021), and by Jepsen-style fault injection.
> This is a learning/research prototype, not production code, and not a formally verified implementation.

## Research questions
1. How do message loss and node crashes affect Raft's **availability and throughput**?
2. Can a **randomized fault injector plus invariant checker** find real Raft bugs? Which bugs does it find, and which hide?

## Design
```
RaftNode          One server as a pure state machine: no threads, sockets or wall clock. Time = tick(); output = a callback.
Network           Lossy, duplicating, reordering network on logical time; can isolate a group of nodes (partition).
Cluster           Drives N nodes + network + faults (crash/restart, partitions, client load). Seeded: a run replays exactly.
InvariantChecker  Checks Election Safety, Leader Completeness, State Machine Safety, Log Matching (Raft paper, Figure 3).
Experiment        The three experiments below; writes results/results.md.
RaftConfig        Timing plus switches that re-create classic bugs (so we can test the checker itself).
```
Because nodes are pure and the only randomness is seeded, **any failure is reproducible from its seed**, which is what makes
this approach useful for debugging as well as testing.

## Method
- 5 nodes, election timeout 150-300 ticks, heartbeat 50, message delay 1-10, one client command every 20 ticks, 10,000 ticks per run.
- After every tick the checker verifies the safety properties; a run stops at its first violation.
- "Time with no usable leader" counts ticks where no live leader can reach a majority (so a stale leader cut off by a partition does *not* count as available).
- Experiments 1-2: 50 seeds per row. Experiment 3: 1000 seeds per variant.

## What the experiments show
- **Safety is cheap to keep, availability is not.** Correct Raft never violated a safety property in any run, even at 40% message loss or
  one crash per 200 ticks. What degrades is *liveness*: at a crash rate of 0.005/tick the cluster spends about 21% of the time without a usable
  leader, and throughput falls from 49 to 38.5 commands per 1000 ticks. Message loss up to 20% costs almost nothing, because heartbeats are
  redundant, then elections start to pile up.
- **Bugs differ enormously in how hard they are to find.** Skipping the election restriction is caught in 87% of runs. Forgetting the vote after a
  restart is caught in only 1.8%: it needs a node to crash between two candidates' campaigns in the same term. Both are found only because the
  checker watches *every* tick.
- **Random fault injection has a blind spot: the Figure 8 bug.** Committing an old-term entry by counting replicas is unsafe, but 0 of 1000 hard runs
  found it, and 0 of more than 20,000 runs across other settings I tried (more crashes, shorter downtimes, narrower election timeouts, crashes aimed at the leader).
  It needs a precise chain of three leaders and two crashes. [`Figure8Test`](src/test/java/raftsim/Figure8Test.java) reproduces it with a hand-written
  schedule: the buggy rule loses a committed entry and the checker catches it; the correct rule survives the identical schedule.
- **A common optimization hides that bug.** If a new leader appends a no-op entry (as real implementations do), the old entry and a current-term entry reach
  followers together, and the Figure 8 schedule cannot even start (the test shows S5 can't win). So a correct-looking system can hide a latent bug
  that only appears when someone removes the optimization.

## Limitations (honest list)
- Logical time and a simplified network: no real clocks, no clock skew, no real sockets, no GC pauses.
- No membership changes, snapshots/compaction, or read-only queries; no client-visible linearizability check, only Raft's internal safety properties.
- "Persistent state" is assumed to be written atomically. Real disks tear writes and lose un-fsynced data (see my `crashcheck` project).
- Randomized testing is not proof. The Figure 8 result shows exactly how it can miss a real bug; a model checker (e.g. TLA+/TLC) or systematic schedule exploration would complement it.
- Liveness is *measured*, not checked: "no usable leader" depends on my definition above.
- One cluster size (5) for the main experiments; the unit tests also run 1, 3 and 7 nodes.

## Future work
- Directed / systematic schedule exploration, so rare interleavings like Figure 8 are found without being hand-scripted.
- Check linearizability of client operations, not just internal invariants.
- Add pre-vote and CheckQuorum and measure how they change outage time after a partition.
- Model torn writes and un-fsynced log entries in the persistence layer (combine with `crashcheck`).

## Reproduce
Needs Java 21 and Maven.
```bash
mvn test                                                    # 47 tests
mvn -q package -DskipTests
java -cp target/classes raftsim.Experiment --seeds 50 --ticks 10000 --bug-seeds 1000 --out results/results.md   # ~10 s
```
The experiment is deterministic: the same arguments always produce the same `results.md`.
